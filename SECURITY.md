# Security Policy

## Supported versions

Security fixes land on the latest release track (`v3.x`). Older releases are not maintained.

## Reporting a vulnerability

Please **do not open a public issue** for a security problem.

Use GitHub's private vulnerability reporting: open the **Security** tab of this repository and choose **Report a vulnerability**. That channel is visible only to the maintainers.

A useful report includes:

- the affected version, tag or commit;
- what the issue is and which component it affects (proxy, monitor, MCP, storage, recording format);
- reproduction steps or a minimal config;
- the impact as you understand it, and any suggested fix.

We aim to acknowledge a report within a few days, agree on a disclosure timeline with you, and credit you in the release notes unless you prefer otherwise.

## Operator notes

Trajecta is local-first, but it handles real credentials and real conversation content, so a deployment still needs care:

- **Cassettes preserve request credentials.** The received HTTP request line (including query values) and request headers are recorded without masking or redaction. The body is captured before proxy normalization, `stream_options` injection, model-alias rewriting, protocol conversion and credential masking. Legacy `debug.mask_key` remains accepted but is deprecated and has no effect; `secret_masking.enabled` can rewrite supported body values before they reach an upstream, but never sanitizes cassette bytes. New recording files are mode `0600` and their day directories are mode `0700`. Treat `trace.output_dir` / `TRAJECTA_OUTPUT_DIR` and its backups as secret-bearing storage; do not commit production recordings.
- **Request-body secret masking only changes what is sent upstream.** `secret_masking.enabled` (on by default, and turned off with an explicit `false`) goes further: a credential or a personal identifier found in a request body (the rule set covers LLM vendor API keys and tokens such as `sk-...` / `sk-ant-...` / `AIza...`, structured tokens such as JWT/JWE, a complete PEM/SSH private-key block, the Chinese resident identity number, and the mainland mobile number; it also masks the value of an env-style `NAME=value` / `NAME: value` assignment found in a request body (tool output, an embedded `.env` or a JSON member) only when the variable name is the uppercase env spelling ending in `_KEY` or `_PASSWORD` (`OPENAI_API_KEY`, `POSTGRES_PASSWORD`; lowercase/camelCase names and `*_TOKEN`/`*_SECRET` are deliberately not masked, so code fragments in tool results are not rewritten), and for a DSN or a URL-class name only the userinfo password, never the whole DSN; a DSN whose scheme is a known database/cache/broker scheme is found without any variable name; a bare eleven-digit run with no phone vocabulary around it is reported but not rewritten) is replaced by a same-length, format-preserving stand-in before the request reaches the provider, the stand-in is restored to the real value in the response, and the cassette still records the *original* body so replay and human inspection keep working. That is deliberate and it is the operator's risk to weigh: the cassette always retains the original request and its real credentials, regardless of `debug.mask_key`; `secret_masking` changes only the supported body values sent to the provider. Query parameters and request headers are not filtered by this feature. The mapping from stand-in back to value is never written to the cassette. It is persisted by default in `<output_dir>/secret_mask_mappings.db`, an embedded bbolt file sealed with the same local key as the audit table (or plaintext when no key exists), so treat it exactly like the cassette directory: it holds the real values and it is the record that lets the next process recognise a stand-in from an earlier session instead of masking it again. It is one installation-wide map keyed by the real value, not partitioned by session or trace; stop `serve` and use `trajecta db secret-mapping stats|list|delete|prune|compact` to inspect it, delete individual pairs, prune the pairs a rule wrote (resolved from `credential_mask_audits`) and rebuild the file (see `docs/SECRET_MASKING.md`). With `secret_masking.mapping_store.enabled: false` the mapping stays process-local - seeded from `crypto/rand` at startup - so a stand-in copied out of a trace cannot be reversed without that process, and a restart invalidates the old stand-ins. The rewrite itself is recorded twice: a `secret.masked` prelude event in the cassette carries the rule and the offsets but no bytes, and one `credential_mask_audits` row carries the real value and the stand-in that replaced it. That table is the per-trace place the pair is stored, and it is the operator's risk to weigh alongside the cassette - the values are sealed with the same local key as the channel credentials when that key exists, and stored in the clear when it does not, with each row's `storage_mode` recording which happened. It is readable through `GET /api/secret-masks` and the MCP tool `list_credential_masks`, so treat it like the cassette directory rather than like a log, and read [docs/SECRET_MASKING.md](docs/SECRET_MASKING.md) before relying on it: it lists what the engine covers and, more importantly, what it does not - truncated or mismatched private-key blocks (a complete block is rewritten; an incomplete one only reports its header), encoded or truncated forms, 15-digit legacy identity numbers, unallocated mobile segments, spaced or hyphenated phone numbers with no eleven-digit run, and operations inside provider-hosted tools that need the real value are all outside it. A private-key stand-in is base64-shaped but deliberately not a parseable key, so a flow that asks the model to parse or validate the key before the response reaches a local tool will fail. The identity-number stand-in keeps a valid province, birthdate and check character but deliberately not the real birthdate, so a flow that cross-checks the number against a separately entered date will disagree; the mobile-number stand-in keeps the allocated three-digit head but re-renders the eight subscriber digits, so a flow that shows or checks the last four digits will disagree too.
- **Structured URL/DSN metadata is redacted; raw cassette requests are not.** Cassette request lines, headers and bodies retain the original query values and credentials. For URLs copied into structured cassette metadata, the `logs` table, a log line or `config inspect`, the shared `redaction.DisplayURL` masks userinfo passwords, query values whose *names* match the marker list (`key`, `token`, `secret`, `password`, `passwd`, `credential`, `signature`, `sig`, `access_token`, `api_key`, `authorization`, `auth`), and userinfo usernames that match the same list. Database DSNs are redacted in both shapes: URL form (userinfo and query string) and keyword form (each `key=value` field). A userinfo username that names no secret, such as a literal API key in `https://sk-live-abc@gateway.example.com/v1`, is retained; put credentials in the encrypted channel API key instead. `debug.mask_key` does not alter raw cassette data.
- **Channel credentials are encrypted at rest.** API keys and secret headers are sealed with AES-256-GCM under a random 32-byte local key stored at `<output_dir>/trace_index.secret` (mode `0600`). Back that file up together with the application database: without it the stored channel credentials cannot be decrypted.
- **The outbound proxy policy is stored in plaintext.** `app_settings.network.proxy` holds the system `http_proxy` / `https_proxy` / `no_proxy` values as submitted, including a `user:pass@` userinfo when the proxy needs authentication; a channel-level policy is stored the same way in `channel_configs.proxy_json`. The system value is read and written only through the admin-only `GET`/`PATCH /api/settings/network-proxy`; the channel value goes through the channel management API. The password is redacted in the startup log, and the channel API returns it as `xxxxx` (saving that placeholder keeps the stored value), but neither value is sealed with the local key the way channel credentials are. Do not put proxy credentials in a URL that is shared, and restrict the Monitor to trusted operators.
- **Authentication is always on, and the admin role is real.** `serve` always opens the auth store: there is no runtime switch that disables token checks on the proxy, the Monitor or MCP. `auth init-user --role admin|viewer` (default `admin`), `auth set-role`, `auth disable-user` and `auth enable-user` control the role and the enabled flag; the Monitor's admin-only surfaces (system diagnostics, channel and plugin configuration, network-proxy/rates settings, pprof) answer 403 to a viewer while the traffic surfaces stay readable. `auth reset-password` also ends every existing Monitor session immediately, and disabling a user rejects their next request: the signed JWT carries a fingerprint of the password hash and is re-checked against the auth store on every request. Personal tokens are independent and are revoked in the Monitor or with the CLI.
- **Personal tokens can be scoped to one surface.** `auth create-token --scope proxy` yields a token the proxy accepts and `/mcp` rejects; `--scope mcp` is the opposite. CLI-created tokens default to `all`; the Monitor token dialog offers `proxy`, `mcp` and `all`, defaulting to `proxy`. Historical `api` scope remains full-access compatible, and unknown scopes are rejected for new tokens. Give an SDK a proxy-scoped token and an MCP client an MCP-scoped one. The `list_credential_masks` tool exposes credential-mask audit values and additionally requires the `admin` role.
- **`/healthz` is the only side-effect-free unauthenticated endpoint.** Both listeners answer `GET`/`HEAD /healthz` with a fixed `{"status":"ok"}` and read nothing; use it for load-balancer and container probes. `GET /api/auth/status` and `POST /api/auth/login` are the only other unauthenticated routes. Login is rate-limited per (client IP, username) — ten failures in fifteen minutes answer 429 with `Retry-After` — and its body is capped at 64 KiB. All Monitor and MCP management routes also have a shared 16 MiB request-body ceiling.
- **pprof is admin-only.** `debug.pprof_enabled` mounts `/debug/pprof/*` behind the Monitor admin gate. A heap profile can contain request bodies and credentials, so keep the switch off unless you are actively diagnosing.
- **Set a strong Compose database password.** `.env.example` leaves `POSTGRES_PASSWORD` blank, and Compose refuses to start until you set a unique URL-safe value; it no longer falls back to an example password. The tracked `config/config.yaml` intentionally contains no provider keys.
- **Keep management access on trusted networks.** Compose binds the gateway and Monitor host ports to `127.0.0.1` by default. Setting `TRAJECTA_HOST_BIND_ADDRESS=0.0.0.0` publishes them on external interfaces; do so only with appropriate firewall/reverse-proxy controls. The Monitor is where provider credentials and recorded traffic are readable. Its API accepts the login JWT, while proxy and MCP use personal bearer tokens. Use separate least-privilege `proxy` and `mcp` tokens, and keep the Monitor port off the SDK network or behind your own access control.
- **Personal tokens are hashed, not recoverable.** Treat a leaked token as compromised and revoke it in the monitor; it cannot be looked up from the database.
